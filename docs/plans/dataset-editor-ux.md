## 1. Диагноз

Редактор сделан как **форма над IR** — промежуточным представлением данных LSS.
Пользователь обязан держать в голове модель: сущность → список грантов → 26 типов →
каналы (числовой / текстовый / ресурсный). Гайд прямо говорит: «редактор сущности =
редактор списка грантов», и это честно реализовано — но это модель *разработчика*,
а не автора хоумбрю. Автор думает «моя раса видит в темноте и даёт +1 к КД», а не
«мне нужен trait с params.range и bonus с target=ac, mode=add».

### Конкретные точки боли

1. **Пустой холст.** `handleCreate` создаёт `{ name: 'Новый датасет' }` и бросает в форму
   метаданных. Гайд §0: «стройте под ревью импорта, а не под пустой холст».
   🟡 Два задизейбленных поля (Идентификатор, Лицензия) убраны из формы в подпись,
   но сам сценарий «пустой холст» остаётся — см. A1.
2. **Первая вкладка — Классы.** Самое сложное и наименее выразимое (§2 «экспрессивный
   обрыв»: кости, ячейки, нечисловые правила класса всё равно уйдут прозой).
   ✅ Порядок вкладок переставлен, дефолт — «Расы».
3. **Слово «грант»** нигде не объяснено кроме тултипа. Дальше — `pairId`, `maxExpr`,
   `expr`, `upgrade/downgrade/multiply`, `casterType`, `progression`.
   🟡 Непереведённые значения (`memory/list/book`, `full/half/third/pact`, категории черт)
   переведены; сам термин «грант» решено оставить (C1 ⛔), `pairId`/`maxExpr`/`expr`
   остаются как есть до E1/E4.
4. **Выбор типа гранта** — плоская сетка из 25 пунктов без поиска, без группировки, без
   описаний. ✅ Заменён на пикер с группами по смыслу, строкой «что это сделает на листе»
   у каждого пункта и поиском по синонимам — см. D.
5. **Смешение языков.** `grantSummary` выдавал `pick 2 from stealth, arcana`, `30 ft`,
   `int / list (full)`; половина линта была на английском.
   ✅ Полностью локализовано. Пути вида `classes/blood-hunter@5/grants[2]` всё ещё
   показываются как есть и никуда не ведут — см. G1.
6. **Три разные модели сохранения на одном экране**: метаданные автосохранялись
   (debounce 500 мс), сущность требовала кнопок Сохранить/Отмена, грант — OK/Отмена.
   «Отмена» в EntityEditor молча выбрасывала всю вложенную работу с грантами.
   ✅ Сведено к одной модели — см. H1.
7. **Ловушки формата не закодированы в UI**, хотя гайд их перечисляет:
   - `max` XOR `maxExpr` — сделано двумя соседними опциональными инпутами; §5.8 явно
     требует переключатель «число / формула». — см. E1.
   - `bonus`: `value` XOR `expr` — та же ошибка, тот же паттерн. — см. E1.
   - §5.10 — было устаревшим уже на момент диагноза: числовые гранты и выборы внутри
     `feat` действительно **не разворачивались**, но LSS починили это 2026-07-29,
     до нашего аудита. У нас в коде уже стояло верное поведение (`grantTypes.ts`:
     `'feat': { ..., note: 'Also expanded for its own grants.' }`) — уезжать в тишину
     нечему. ✅ Ложная тревога, E3 закрыт без реализации — см. E3.
   - Свободный ввод формул (`[f:...]`, `expr`, `maxExpr`) — §5.3 просит этого не делать.
     ⛔ Решено оставить свободный ввод (E2).
8. **Нет предпросмотра.** Автор ни разу не видит, что получится на листе. Модель каналов
   невидима: что описание черты с `params` потеряется, узнаёшь только из линта постфактум.
   — см. F.
9. **Опасные операции без подтверждения.** ✅ Удаление датасета теперь спрашивает
   подтверждение. `localStorage` при переполнении по-прежнему падает молча — см. E6.
10. **Разнобой в глоссарии**: ExtractPanel — «Фоны»/«Фиты», EntityList — «Предыстории»/
    «Черты», DatasetList — «предысторий»/«черт». ✅ Сведено в один модуль.
11. **Мелочи, читающиеся как небрежность**: «Нет классы», «отобразиться» без мягкого
    знака, поле «Английское название» даёт английский `label`. ✅ Все три исправлены.
12. **Нет поиска/фильтра** в списке сущностей — на датасете из 80 черт это стена.
    🟡 Поиск есть; фильтра «только с ошибками» нет — см. B3.
13. **Нет выхода наружу как явного шага.** Экспорт — иконка 15px в карточке. Гайд §7:
    «без пути наружу редактор бессмысленен». — см. K1.

## 2. Предложения

### A. Онбординг и точка входа

- **A1. Убрать пустой холст.** Экран «Создать» → выбор сценария: «Хоумбрю-раса» /
  «Хоумбрю-черта» / «Подкласс к SRD-классу» / «Предыстория» (создают датасет с уже
  заведённой сущностью нужного вида), «Импортировать JSON», «Начать с примера»
  (предзаполненный датасет-образец), и лишь последним — «Пустой датасет».
- **A2. Шаблоны сущностей.** При добавлении расы/черты предлагать скелет: раса уже с
  `speed 30`, `size medium`, слотом под тёмное зрение; черта происхождения — с
  `category: origin`. Сейчас `makeEmptyEntity` даёт голый объект.
- **A3. ✅ Переставить вкладки** в порядке гайда §7: Расы → Подрасы → Предыстории →
  Черты → Подклассы → Классы; дефолтная вкладка — «Расы».
  Осталось: честная плашка у вкладки «Классы» — «класс механизируется частично:
  кости и нечисловые правила уйдут текстом».
- **A4. Первый запуск** — три карточки поверх пустой библиотеки: «Что такое датасет» /
  «Соберите первую расу за 5 минут» / «Как подключить готовый датасет в LSS».

### B. Информационная архитектура

- **B1. ✅ Свернуть метаданные.** ID и лицензия стали строкой-подписью под заголовком

  Редакция. Перенос «Версии» в блок «Публикация» отпал вместе с H2 ⛔.
- **B2. Двухпанельный режим для редактирования.** Слева дерево датасета, справа форма.
  Сейчас навигация — стек полноэкранных состояний (`library → edit → entity → grant`)
  с потерей контекста на каждом шаге.
- **B3. 🟡 Поиск и фильтр** в списке сущностей. Поиск по названию и id сделан
  (появляется от 7 элементов). Осталось: фильтр «только с ошибками».
- **B4. ✅ Экран сущности изолирован** (2026-07-30). Пока сущность открыта, прячутся
  заголовок «Редактирование: …», подпись `id · лицензия`, индикатор автосохранения,
  форма метаданных (Название / Автор / Версия / Редакция) и кнопка «Назад» в библиотеку.
  Остаётся панель линта и сама сущность со своей стрелкой возврата к списку — то есть
  ровно один способ уйти назад и ни одного поля не про эту сущность.
  `EntityList` сообщает состояние наверх через `onEditingChange`; в `DatasetEditor`

### E. Защитные ограждения (кодируем гайд в UI)

- **E1. `max`/`maxExpr` и `value`/`expr` — переключатель «Число ⇄ Формула»**, а не два поля.
  Убирает два самых частых error’а линта до их появления.
- **E2. ⛔ Конструктор формул** вместо текстового поля (§5.3). Решено не делать: свободный
  ввод формул остаётся. Практическое следствие — ошибки в формулах ловит только линт и
  рантайм LSS, поэтому E1 (явный выбор «число или формула») становится важнее.
- **E3. ✅ Закрыт без реализации — предпосылка не подтвердилась.** Была задумана как
  предупреждение при числовых грантах внутри черты (§5.10 гайда на момент диагноза).

  **Что предполагалось.** Гайд на дату диагноза утверждал, что черта (`feats[]`) — не
  прозрачный контейнер: числовой канал и пикеры выбора (`skill-choice`,
  `expertise-choice`) не разворачивают её собственные гранты, только текстовый и
  ресурсный. Отсюда идея — линтить `feats/<id>/grants[i]` и предупреждать, что такой
  грант не доедет до листа.

  **Почему не делаем.** Уже в момент диагноза это было неверно — наша собственная
  встроенная пометка это заметила («черты как минимум уже умеют выдавать грант Навыки
  (выбор), и визард их рендерит»), и проверка подтвердила: LSS починили разворот
  `feat` во все каналы 2026-07-29 (`storyview` коммит про expand feat grants), **до**
  даты нашего диагноза. У нас в `grantTypes.ts` уже стояла верная запись
  (`'feat': { ..., note: 'Also expanded for its own grants.' }`) — предупреждать
  не о чем, числовые/выборные гранты внутри черты доезжают до листа как обычно.
  Правило линта строить не будем — его предпосылка ложна.

  **Единственное реальное узкое исключение (не про `feat`, отдельная история):**
  `skill-choice` конкретно на предыстории (авторенный прямо на ней или раскрытый из
  её `feat`) сегодня не даёт слот/счётчик в визарде — пикер навыков читает
  раскрытые гранты предыстории только на `skill-fixed`. Это не контейнерность
  черты, а отдельный, гораздо более узкий пробел именно у предыстории. Если
  захотим лечить это линтом — это отдельная, маленькая задача, не переиспользование
  E3.
- **E4. Форма ресурса ведёт за руку**: сначала «к какой способности относится счётчик»
  (выбор из черт сущности + кнопка «создать описание»), потом максимум, потом отдых.
- **E5. 🟡 Мягкие подтверждения.** Удаление датасета спрашивает подтверждение (инлайн
  «Удалить / Нет», как у сущности). Осталось: тост «Отменить» после удаления.
- **E6. Реакция на переполнение localStorage** вместо `catch {}` в `storage.ts` — сейчас
  данные теряются молча.

### F. Живой предпросмотр — главный рычаг понимания

Панель «Как это выглядит на листе» рядом с формой: слайдер уровня 1–20 и рендер того, что
сущность реально даёт — числа, текстовые блоки, счётчики, по каналам. Тогда видно:
пропавшее описание черты с `params` (§5.5), работу `leveledGrants`, мёртвый таргет `bonus`.
Дорого, но объясняет модель без единого слова документации. Даже упрощённый вариант
(«сводка эффектов текстом») даёт большую часть пользы.

### G. Линт как помощник, а не лог компилятора

- **G1. Кликабельные ошибки**: `classes/blood-hunter@5/grants[2]` → «Кровавый охотник →
  уровень 5 → грант №3», по клику открывается нужная форма.
- **G2. Группировка по сущностям** вместо плоского списка.
- **G3. Быстрые фиксы**: «Убрать expr» / «Поставить pairId: null» / «Создать описание».
- **G4. Разделить «ошибка» и «предупреждение» по смыслу для автора**: «не поедет на лист»
  vs «поедет, но не туда».
- **G5. Зелёное состояние**: «Замечаний нет — датасет готов к выгрузке».

### H. Модель сохранения и безопасность работы

- **H1. ✅ Один режим сохранения везде — сделано 2026-07-30.** Метаданные датасета,
  поля сущности и поля гранта теперь все ведут себя одинаково: правка пишется в
  состояние `ds` в `DatasetEditor` немедленно, а запись в `localStorage` и перелинт —
  единый debounce 500 мс (индикатор «сохранено / сохраняется…» в шапке относится ко
  всему экрану, а не только к метаданным).
  - `EntityEditor`: убран локальный буфер `data` + кнопки «Сохранить»/«Отмена».
    Каждое изменение поля идёт через `onChange` сразу в `EntityList`, а дальше —
    в `ds`. Кнопка «Отмена» заменена на «Готово» (просто закрывает форму, ничего
    не отбрасывает); подтверждение удаления (E5) осталось как было.
  - `EntityList`: сущность заводится в датасет сразу в момент подтверждения имени
    (`handleConfirmAdd`), а не откладывается до первого «Сохранить» — поэтому больше
    нет разрыва между «сущность создана в UI» и «сущность существует в данных».
  - `GrantEditor`/`GrantList`: та же схема — «OK»/«Отмена» заменены на «Готово»,
    правки гранта пишутся в список грантов сущности по мере ввода.
  - Из диагноза (п. 6): «Отмена» в EntityEditor больше не может выбросить вложенную
    работу с грантами, потому что отбрасывать больше нечего — всё уже сохранено.

  **Проверка:** `npx tsc --noEmit` чисто; `next lint` по изменённым файлам — новых
  ошибок нет (остались прежние `no-explicit-any`/`exhaustive-deps`, см. L). Ручная
  проверка в браузере не проводилась — см. заметку ниже.
- **H2. ⛔ Черновик / опубликовано.** Решено не делать. Следствие, о котором стоит помнить:

### J. Импорт как основной сценарий (совет гайда №1)

Гайд утверждает: главный экран — **не создание, а ревью импорта**. Dimension Door научится
тянуть классы/расы и начнёт выдавать черновики с ошибками; редактор ценен как мастерская
починки черновиков.

- **J1. Режим «починить импорт»**: после импорта не карточка «OK», а пошаговый проход по
  замечаниям («3 места требуют внимания» → Далее → Далее).
- **J2. Вставка из текста**: копируем статблок с dnd.su → черновик сущности (заголовок →
  label и id-слаг, «Скорость 30 футов» → грант скорости). Даже примитивный парсер по
  ключевым фразам снимает основную массу ручного ввода.
- **J3. 🟡 Диф при повторном импорте** того же id. Пока сделано только одно: подтверждение
  перезаписи переведено на русский; самого дифа нет.
